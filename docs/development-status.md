## 같이 달리기 방 (2026-10-27)

- (아래 '친구 요청 방식으로 변경'에서 코드 참가·공개 목록을 없앴다)
- 커뮤니티 → 같이 달리기: 방 만들기(이름·목표 거리·최대 인원), 코드로 참가, 대기 중인 방 목록, 나가기.
- 서버 함수 `roomAction`(asia-northeast3): list/create/join/start/leave/finish를 트랜잭션으로 처리한다.
  한 사람은 한 방에만 참가, 방장만 시작, 정원 초과·시작된 방 참가 차단, 방장이 나가면 남은 사람에게 위임, 모두 나가거나 완주하면 종료.
- 달리는 중에는 각자 거리·페이스를 `together_rooms/{id}/members/{uid}`에 올리고, 실시간 상위 3명 순위를 달리기 화면에 띄운다.
- 완주하면 일반 달리기와 같은 기록으로 저장(같은 세션 재시도 시 중복 저장 없음)한 뒤 방에 완주를 알린다.
- `dalryo-dev`에 함수·규칙·인덱스 배포 완료. 에뮬레이터 백엔드 통합 시나리오 11개 통과.
- ADB: 같이 달리기 화면 진입과 배포된 함수의 방 목록 조회 성공을 확인했다. 상태 표시줄 아이콘이 흰색으로 보이던 문제를 고쳤다.
- 실제 방 생성·두 기기 동시 달리기는 다른 사용자 목록에 노출되므로 실행하지 않았다(백엔드 테스트로 대체).

## 2026-10-29 · 달리기 기록 안정화

- Android에 `RunTrackingService`와 RN 브리지를 추가했다. 사용자 시작 동작에서 위치 foreground service를 실행하고, GPS 수집·거리·경로·시간을 JS 타이머와 독립적으로 기록한다. 지속 알림으로 앱에 돌아올 수 있다. 위치는 정확도 25m 이내, 45km/h 이상 점프 제외, 30초 이상 GPS 공백 미합산, 경로 최대 6,000점(초과 시 간추림)으로 제한한다.
- `AtomicFile`에 각 수신 위치와 5초 간격 체크포인트를 저장한다. Android 시간은 monotonic clock을 사용한다. 강제 종료 후에는 마지막 체크포인트를 일시정지로 복구하며, 앱이 기록하지 못한 구간은 추정하지 않는다. 일시정지·종료·버리기에는 위치 서비스를 정리한다. 이미 다른 계정의 진행 기록이 있으면 새 기록으로 덮어쓰지 않는다.
- iOS는 기존 Core Location watch에 background location 설정과 Info.plist location mode를 연결했다. 새 AsyncStorage 의존성은 Mac에서 Pods 설치 후 빌드/실기기 검증이 필요하다. Windows에서 iOS 실행을 검증했다고 보지 않는다.
- 시작 시점의 목표·공원·코스·성장 상태·체중·같이 달리기 roomId를 진행 기록에 함께 보관한다. 재실행 복구 화면에서 이어 달리기/마무리 저장/명시적 버리기를 선택할 수 있다.
- 완료 기록은 계정별 AsyncStorage outbox에 먼저 보관한 뒤 서버로 보낸다. 서버 저장 대기가 8초를 넘으면 기기 사본을 유지한다. 앱 실행/전경 복귀/전경 15초 주기로 재시도한다. 앱 삭제 시 기기 사본은 보존되지 않으며, 종료된 앱에서 업로드하는 OS 작업 스케줄러는 추가하지 않았다.
- UID+시작 시각의 기존 run_id를 재사용하고 서버 확인 후 대기열에서 제거한다. 자동 저장과 수동 재시도가 경쟁해도 이미 저장된 같은 기록을 돌려준다. 다른 계정의 대기 기록은 업로드하지 않는다. 같이 달리기는 기록 저장 후 방의 종료 상태를 재시도하며, 이미 닫혔거나 떠난 방을 재생성하지 않는다.
- 즉시 종료의 duration은 서비스/저장 경계에서 최소 1초로 보정한다. 계정 변경 후 늦게 도착한 이전 계정 응답이 복구 화면을 덮던 문제도 회귀 테스트로 수정했다.
- Android APK 빌드/설치 성공. ADB에서 실제 foreground location service(type=location, notification 4107)를 확인했다. 화면 OFF 상태에서 elapsed 10초→75초와 테스트 좌표 이동(경로점 1→3, 약 17.5m)이 기기에 남았다. 이후 26.4m·115,490ms에서 강제 종료 후 복구 화면(0.03km/1:55, interrupted=true)을 확인했고, 재개 시 elapsed 125,583ms로 이어졌다. 테스트는 취소하여 복구 파일과 위치 서비스가 사라짐을 확인했다. 실제 사용자 서버 기록이나 보상을 테스트 목적으로 생성하지 않았다.
- 오프라인 전송/응답 유실/디스크 오류/중복 저장/계정 격리/닫힌 방 처리는 Jest 모의 네트워크로 검증했다. 실제 기기 배터리 제한·장시간 실주행·iOS 및 두 기기 같이 달리기 재검증은 남아 있다.
- Windows 빌드는 설치된 JDK 17을 사용했다. JDK 25에서 기존 RN toolchain resolver 호환 오류가 있었고, Java Unix socket 임시 경로는 짧은 프로젝트 `.build-tmp`로 설정했다. Gradle/React Native 의존 파일을 임의 패치하지 않았다.

플랫폼 참고: [Android foreground service 시작 조건](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [Apple background location 설정](https://developer.apple.com/documentation/corelocation/cllocationmanager/allowsbackgroundlocationupdates).

최종 검증: Jest 27개 스위트/165개 테스트, TypeScript, ESLint, diff 공백 검사 통과. Android debug APK 최종 빌드 성공 및 에뮬레이터에 업데이트 설치.

- 원인(코드 분석, 실기기 로그로 확인한 것은 아님): ① 위치가 JS에 도착한 시각이 측정 시각보다 15초 넘게 늦으면 버렸다. 화면이 꺼진 동안 쌓인 위치가 한꺼번에 들어오면 대부분 버려졌다. ② 남은 위치끼리 30초 넘게 떨어져 있으면 그 구간 거리를 통째로 더하지 않았다. 경로점은 계속 쌓여서 지도선은 정상으로 보였다.
- 수정: ① 도착 시각으로 버리지 않고 각 위치의 측정 시각으로 이어 계산한다. 달리기 시작·재개 직전에 측정된 캐시 위치만 시작 시각으로 거른다. ② 30초~30분 간격은 직선거리 평균 속도가 25km/h 이하일 때만 더하고, 그보다 빠르거나 30분을 넘으면 기존처럼 잇지 않는다. 짧은 간격의 45km/h 초과 튐 제거와 정확도 25m 제한은 그대로다.
- 회귀 테스트 5개 추가: 한꺼번에 늦게 도착, 드문드문 도착, 비현실적 속도·너무 긴 공백, 시작 전 캐시 위치, 순서가 뒤바뀐 중복. 앱 전체 Jest 291개 통과.
- 미확인: iOS 실기기 재검증과, 정확도 25m 제한이 주머니 속에서 위치를 너무 많이 버리는지 여부. Android 네이티브 `RunTracking.kt`는 수정하지 않았다(포그라운드 서비스로 위치를 제때 받고 화면 OFF 상태 검증이 이미 있다).

## 2026-11-02 · 알림 아이콘과 알림에서 바로 이동

- 알림 왼쪽 동그라미: 사람이 한 행동(팔로우·응원·댓글·같이 달리기 요청)은 상대 프로필 사진을 보여 주고(없으면 사람 아이콘) 오른쪽 아래에 행동 아이콘을 붙인다. 성장은 성장 아이콘, 돌 경고는 산/눈 아이콘, 설정 알림은 설정 아이콘, 모르는 종류는 종 아이콘이다.
- 알림을 누르면 이동한다: 응원·댓글 → 그 게시물(피드 위에 열리고 뒤로 가면 피드), 새 팔로워 → 그 사람 프로필, 같이 달리기 요청 → 같이 달리기, 성장 → 성장 탭, 돌 경고 → 홈, 설정 알림 → 설정. 대상 정보가 없는 옛 알림은 기존처럼 안내 창만 보여 준다.
- **서버 배포 필요:** 알림 문서에 `actor_image`(상대 프로필 사진 주소)를 저장하도록 `functions/src/social.ts`와 `functions/src/rooms.ts`를 고쳤다. 아직 배포하지 않았다. 배포 전에는 새 알림도 사진 대신 사람 아이콘이 보인다. 이미 쌓인 옛 알림에는 사진이 없어 계속 사람 아이콘이다. 앱 쪽은 사진이 없어도 정상 동작한다.
- 설정 알림(`settings`)은 이동·아이콘만 준비해 둔 이름이며 아직 서버가 만들지 않는다. 푸시 알림을 눌러 앱을 열면 지금은 알림 목록이 열리고, 해당 대상으로 바로 가지는 않는다.

## 2026-11-02 · 스와이프 뒤로가기와 탭 스와이프

- **iOS 왼쪽 가장자리 스와이프 뒤로가기:** iOS의 `BackHandler`는 아무 일도 하지 않는 빈 껍데기라 화면마다 등록한 뒤로가기(Android용)가 실행되지 않았다. `src/navigation/backGesture.tsx`가 iOS에서만 등록을 가로채 보관하고, 화면 왼쪽 16px 띠에서 오른쪽으로 60px 넘게 쓸면 Android와 같은 순서(나중에 등록한 화면부터, true를 돌려주는 화면에서 멈춤)로 호출한다. 화면 코드는 바꾸지 않았다. `index.js`에서 화면을 그리기 전에 켠다. Android는 시스템 뒤로가기를 그대로 쓴다.
- **탭 스와이프:** 홈·성장·커뮤니티·기록에서 가로로 쓸면 탭이 바뀐다(`src/navigation/tabSwipe.ts`). 오른쪽→왼쪽은 다음 탭(홈→성장→커뮤니티→기록), 왼쪽→오른쪽은 이전 탭이며 양 끝에서는 멈춘다. 가로가 세로의 2배 넘게 크고 60px 이상일 때만 인식해 세로 스크롤과 구분한다. 커뮤니티·기록의 하위 화면(게시물, 채팅, 기록 상세 등)과 설정·알림 같은 전체 화면에서는 꺼진다.
- 한계: 왼쪽 16px 띠에서 시작한 터치는 뒤로가기 전용이라 그 자리의 버튼은 눌리지 않는다. 시작 화면·전화번호 입력처럼 뒤로가기를 등록하지 않은 화면은 스와이프로 뒤로 가지 않는다. 달리기 중 스와이프 뒤로가기는 Android 뒤로가기와 같이 그만둘지 묻는 확인 창을 띄운다. 댓글 시트 같은 모달 안에서는 동작하지 않는다. (화면이 밀리는 애니메이션은 아래 '화면 전환 애니메이션' 항목에서 추가했다.)
- Jest로 규칙과 연결을 검증했다. iOS 실기기 확인은 하지 않았다.

## 2026-11-02 · 화면 전환 애니메이션

- **탭 전환(`src/navigation/tabPager.tsx`):** 홈·성장·커뮤니티·기록을 가로 한 줄에 놓인 것처럼 다룬다. `position`(화면 가운데에 오는 탭 번호, 소수 가능) 하나로 각 탭이 (자기 번호 − position) × 화면 너비만큼 옆으로 밀려 있다. 손가락을 따라 움직이다가 놓으면 화면 너비의 20% 이상 끌었거나 빠르게 튕겼을 때 다음 탭으로, 아니면 원래 탭으로 자리를 잡는다. 맨 끝 탭 너머로 끌면 저항이 생긴다. 하단 탭 바를 눌러도 같은 방식으로 슬라이드한다(멀리 있는 탭은 가운데 탭 없이 바로 밀려 온다). position이 절대 번호라 전환이 끝나도 값을 되돌리지 않아 끝나는 순간 화면이 튀지 않는다. 끌기 시작하면 옆 탭을 그때 그려서(마운트) 그 탭의 조회가 시작된다.
- **밀려 들어오는 화면(`src/navigation/slide.tsx`, `slideRegistry.ts`):** 설정, 알림, 보관함, 공원, 같이 달리기, 개발용 캐릭터 미리보기는 탭 화면을 지우지 않고 그 위에 오른쪽에서 밀려 들어오고, 뒤로 가면 오른쪽으로 밀려 나간다. 탭 화면이 아래에 그대로 남아 있어 돌아오면 스크롤 위치와 상태가 유지되고(예전에는 다시 불러왔다), 열려 있는 동안 화면 읽기 기능에서는 가려진다. 커뮤니티의 하위 화면(게시물, 프로필, 채팅, 글쓰기, 검색, 랭킹, 저장함, 관계 목록)과 기록의 상세(러닝 저널)도 같은 방식이며, 쌓인 화면이 모두 그대로 아래에 남는다.
- **iOS 가장자리 드래그:** 왼쪽 가장자리를 잡고 끌면 맨 위 화면이 손가락을 따라 오른쪽으로 움직이고, 화면 너비의 30% 이상 끌었거나 빠르게 튕겼을 때 뒤로 간다. 뒤로가기는 그 화면이 등록한 처리를 거치므로 저장하지 않은 설정처럼 확인 창이 있으면 확인을 받고, 닫히지 않으면 제자리로 돌아온다. Android는 화면의 뒤로가기 버튼과 시스템 뒤로가기에서 밀려 나가는 애니메이션만 적용된다(가장자리 드래그는 없다).
- **적용하지 않은 곳:** 달리기 흐름(목표 설정, 달리기 중, 저장, 완료), 완료 화면 안의 공유·기록 상세 전환, 오운완 카드로 들어가는 전환, 가입·로그인 화면, 모달(댓글 시트 등)은 이전처럼 즉시 바뀐다.
- 애니메이션은 `src/navigation/motion.ts`의 설정으로 한 곳에서 켜고 끈다. 테스트에서는 `jest.setup.js`가 꺼서 바로 끝난 상태로 검증한다. Jest로 전환 로직(어느 화면이 되는지, 위치 계산, 되돌리기)은 검증했지만 실제 부드러움과 프레임은 기기에서 확인하지 못했다.

## 2026-11-02 · 커뮤니티 헤더 정리와 하단 서브 네비게이션
- **헤더:** 홈·성장·기록과 같은 `ScreenHeader`(제목 "커뮤니티", 알림·설정 40px)로 바꿨다. "달료 클럽"과 "함께 달리는 이야기" 문구, 프로필·검색·메시지 아이콘은 헤더에서 뺐다.
- **피드:** 전체/팔로잉/내 게시물 선택을 없애고 전체 공개 피드만 보여 준다. 팔로잉 피드는 화면에서 열 방법이 없어졌다(`useSocialFeed`는 그대로 지원한다). 전체 공개가 아닌 글을 쓰면 피드에 보이지 않으므로 저장 후 내 프로필을 열어 준다.
- **서브 네비게이션(`CommunitySubNav`):** 기존 하단 탭 바 바로 위에 작게 놓인다. 평소에는 가운데에 둥근 메뉴 버튼 하나만 있고, 누르는 즉시 양옆으로 피드·탐색·메시지·프로필이 펼쳐진다. 누른 채 끌어 메뉴 위에서 놓으면 이동하고, 메뉴가 아닌 곳에서 놓으면 접힌다. 끌지 않고 톡 눌렀다 떼면(0.3초 이내) 펼쳐진 채로 남아 눌러서 고를 수 있고, 화면 읽기 기능에서는 메뉴 버튼의 동작 목록으로 바로 고른다. 지금 보고 있는 메뉴는 펼쳤을 때 표시된다.
- **메뉴 동작:** 피드·탐색(러너 검색)·메시지(채팅 목록)·프로필(내 러너 프로필)은 커뮤니티 안의 "섹션"이다. 고르면 메인 하단 바와 서브 네비게이션은 그대로 둔 채 그 위쪽 영역만 바뀐다(피드는 아래에 그대로 남아 있어 스크롤 위치가 유지된다). 이미 보고 있는 피드를 다시 고르면 맨 위로 올리고 새로고침한다. 섹션 화면의 뒤로가기는 피드로 돌아온다. 안 읽은 메시지가 있으면 메뉴 버튼과 메시지 메뉴에 점이 뜬다.
- **하단 바가 가려지는 경우:** 섹션 위에 게시물·다른 러너 프로필·글쓰기·팔로우 목록 등이 쌓이거나, 메시지에서 대화방·새 대화로 들어가면(키보드 때문에) 두 하단 바를 모두 가리고 화면을 꽉 채운다. 닫으면 다시 나타난다.
- 하단 탭 바의 높이와 띄우는 거리(`TAB_BAR_BODY_HEIGHT`, `tabBarBottom`)를 내보내 서브 네비게이션 위치가 같은 값을 쓴다. Jest로 메뉴 위치 계산과 길게 누르기·끌기·놓기 흐름은 검증했지만 실제 손맛(길게 누르는 시간, 끌 때 걸리는 정도)은 기기에서 확인하지 못했다.

## 2026-11-02 · 커뮤니티 메뉴 화면 정리, 탐색 피드, 아이디
- **하단 잘림 수정:** 탐색·메시지·프로필 화면이 하단 바 위에서 끊기지 않고 화면 맨 아래까지 이어진다. 두 하단 바는 그 위에 떠 있고, 끝까지 스크롤하면 마지막 내용이 바에 가려지지 않도록 화면별로 끝에 여백(`bottomInset`)을 둔다. 대화방은 키보드 때문에 예전처럼 바를 가리고 꽉 채운다.
- **서브 네비게이션 이름:** 프로필 메뉴는 "내 프로필"로 보인다.
- **피드와 탐색(서버가 목록을 만든다, `socialAction`):**
  - **피드(`homeFeed`):** 내가 팔로우한 사람과 내 글을 최신순으로 보여 주고, 4개마다 추천 글 하나를 끼운다. 팔로우 글이 먼저 떨어지면 남은 추천 글이 이어진다. 아무도 팔로우하지 않았으면 전부 추천 글이다. 팔로우한 사람의 팔로워 공개 글도 보인다.
  - **탐색(`exploreFeed`):** 내가 팔로우하지 않은 사람들의 공개 글만, 내 글은 제외하고 무작위 순서로 보여 준다. **추천 기준은 아직 없고 나중에 정한다**(`functions/src/explore.ts`의 `recommendations`에서 순서만 바꾸면 된다). 피드의 추천 글도 같은 후보를 쓴다.
  - 둘 다 10개씩 나눠 받고(당겨서 새로고침, "더 보기"/"더 둘러보기"), 후보는 최근 공개 글 200개다. 새로고침할 때마다 앱이 새 `seed`를 만들어 보내고, 같은 새로고침 안의 "더 보기"는 같은 seed를 써서 앞에서 본 글이 다시 나오거나 빠지지 않는다.
  - 예전 피드는 실시간으로 갱신됐지만 이제는 요청 방식이다. 내가 글을 올리면 서버 저장이 끝난 뒤(백그라운드) 피드를 자동으로 다시 불러온다. 다른 사람의 새 글은 당겨서 새로고침해야 보인다.
  - 전체/팔로잉/내 게시물로 가르던 `useSocialFeed`와 `watchFeed`는 화면에서 더 쓰지 않는다(코드에는 남아 있다). 내 글만 모아 보는 곳은 프로필이다.
  - 러너 검색은 탐색 화면 오른쪽 위 돋보기 버튼으로 열고, 닫으면 탐색으로 돌아온다.
- **아이디(`user_id`):** 영문 소문자·숫자·밑줄 4~20자, 겹치지 않는다. `handles/{아이디}` 문서를 먼저 차지한 사람의 것이다.
  - **가입:** 첫 단계에 "아이디" 입력이 생겼고 필수다. 다음으로 넘어갈 때 이미 쓰는 아이디면 바로 알려 주고(확인하지 못하면 그대로 진행), 가입 저장 때 사용자 문서와 같은 트랜잭션으로 한 번 더 확인해 차지한다.
  - **설정:** 내 프로필 항목에 "아이디" 입력이 있다. 서버(`saveAccountSettings`)가 새 아이디를 차지하고 이전 아이디를 놓아 준다. 이미 정한 아이디는 비울 수 없다.
  - **표시:** 러너 프로필 맨 위(예전에는 "러너 프로필")에 `@아이디`가 보인다. 아직 아이디가 없는 기존 사용자는 닉네임이 보인다. 검색 결과에도 `@아이디`가 붙고, 검색창에 `@`로 시작해 입력하면 아이디로 찾는다.
  - 기존 사용자는 아이디가 비어 있다. 설정에서 정하기 전까지는 닉네임으로 보인다(강제로 정하게 하지는 않는다).
- **서버 배포 범위(아래 점검 항목에서 배포함):** `socialAction`(피드·탐색 목록, 아이디 검색, 프로필의 `user_id`), `saveAccountSettings`(아이디 저장), `firestore.rules`(`handles` 컬렉션과 `users.user_id` 허용). 가입 화면의 아이디 확인과 저장은 규칙이 배포돼야 동작한다. 배포 전에는 가입이 막히므로 **반드시 규칙을 먼저 배포한 뒤** 앱을 내보내야 한다.

### 피드·탐색 불러오기 실패 점검 (2026-11-02)
- **증상과 원인:** 피드·탐색이 "불러오지 못했어요"로 뜬다. 에뮬레이터 기기에서 확인한 서버 응답은 `invalid-argument / 항목을 찾을 수 없어요.`다. 배포된 `socialAction`에 `homeFeed`·`exploreFeed`가 없어서, 요청이 게시물 전용 코드의 `documentId(input.postId)`까지 내려가 나는 오류다. 앱 코드 문제가 아니라 서버 미배포 때문이다.
- **컴파일 오류 수정:** `postDto`의 반환 타입 때문에 `functions`의 `tsc`가 실패하고 있었다. `firebase.json`의 predeploy가 빌드를 돌리므로 이 상태로는 배포 자체가 멈췄다. 타입을 명시해 고쳤다.
- **규칙 보완:** `users` 문서를 만들 때 `user_id`의 `handles` 문서 주인이 본인인지 확인한다. 이전에는 남의 아이디를 프로필에 적을 수 있었다.
- **검증:** 에뮬레이터에서 `scripts/test-firestore-rules.cjs` 16개, `scripts/test-social-functions.cjs` 23개 통과(피드·탐색 구성, 아이디 차지·중복 거절·변경, `@` 검색 시나리오 추가). 에뮬레이터는 복합 색인을 검사하지 않는다. 두 쿼리는 기존 피드·팔로잉 피드와 같은 형태라 `firestore.indexes.json`의 기존 색인을 쓴다. 실제 서버에서는 아직 확인하지 못했다.
- **배포:** 사용자가 직접 실행했다. `npx -y -p firebase-tools firebase deploy --only functions:socialAction,functions:saveAccountSettings,firestore:rules --project dalryo-dev`. 에뮬레이터 기기에서 피드가 게시물을 불러오는 것을 확인했고, 배포 후 `socialAction` 로그에 오류 등급 기록은 없었다. 탐색 화면과 실제 서버의 아이디 저장·가입은 아직 기기에서 확인하지 못했다.
- **에뮬레이터 실행 메모:** 이 저장소에 `firebase-tools`가 설치돼 있지 않아 `npx firebase`는 동작하지 않는다. `npx -y -p firebase-tools firebase emulators:exec ...`로 실행하고, 그 전에 `npm --prefix functions ci`와 `npm --prefix functions run build`가 필요하다. Java 21 이상(Android Studio JBR)을 쓴다.

## 2026-11-02 · 커뮤니티 피드·탐색·메시지 정리
- **피드:** "러닝 이야기 / 각자의 속도, 함께 나누는 한 걸음" 머리글과 "저장함" 버튼을 없앴다. 윗줄에는 "같이 달리기"와 "러너 랭킹" 두 개가 한 줄로 남는다. 글쓰기는 오른쪽 아래의 원형 버튼(연필 아이콘)이 되었고, 서브 네비게이션이 펼쳐지면 그 위로 비켜 올라갔다가 접히면 돌아온다. 서브 네비게이션과 글쓰기 버튼이 같은 애니메이션 값(`progress`)을 쓰므로 상태가 바뀌길 기다리지 않고 메뉴와 같은 순간에 같이 움직인다. 글쓰기 버튼은 피드와 탐색 화면에서 보인다(메시지·내 프로필에는 없다). 탐색에서 글을 올리면 피드로 돌아온다.
- **저장한 게시물:** 설정 목록에 "저장한 게시물" 항목이 생겼다. 누르면 설정을 닫고 커뮤니티의 저장한 게시물 화면이 열리며, 뒤로 가면 커뮤니티 피드로 돌아온다(`CommunityLink`에 `saved` 추가).
- **탐색:** "DISCOVER / 아직 팔로우하지 않은 러너들의…" 안내 문구를 없앴다.
- **메시지:** 오른쪽 위 새 대화 아이콘을 메시지 모양에서 `+`로 바꿨다. "팔로잉·팔로워에서 찾기" 버튼과 "RUN TOGETHER, TALK TOGETHER" 문구를 없애고, 맨 위에 "같이 달리기" 버튼을 두었다.
- **새 대화 검색 순서:** 내가 팔로우한 사람 > 나를 팔로우한 사람 > 모르는 사람 순이다(서로 팔로우하면 팔로잉). 결과 줄에 "팔로잉" / "나를 팔로우" 표시가 붙는다. 서버(`socialAction`의 `search`)가 관계를 붙여 정렬하고 앱도 같은 순서를 지킨다. 같은 관계 안에서는 닉네임 순이며, 후보는 닉네임 앞부분이 맞는 최대 50명이다(한 번에 50명을 넘는 이름 앞부분을 쓰면 뒤쪽 사람은 잘린다).
- **서버 배포 필요:** 검색 순서는 `socialAction` 배포 후에 적용된다. 배포 전에는 순서만 이름순이고 나머지 화면은 그대로 동작한다.
- 에뮬레이터 서버 시나리오 24개 통과(검색 순서 추가), 앱 테스트·`tsc`·`eslint` 통과.

## 2026-11-03 · 로딩 화면, 댓글 스레드·삭제, 게시물 메뉴·차단
- **앱 시작 로딩:** 홈을 로딩 화면 아래에서 미리 그려 두고, 다 그려진 뒤에 로딩 화면을 걷는다(`App.tsx`). "다 그려짐"은 캐릭터(PNG는 이미지 로드 완료, Rive는 재생 시작, 받지 못한 경우 포함)와 이번 주 기록 응답이 모두 끝난 때다. 인터넷이 느려도 갇히지 않도록 10초(`HOME_READY_MAX_MS`)가 지나면 걷는다. 시작·로딩·홈 대기 화면이 트리의 같은 자리에 있어 배경 이미지가 끊기지 않는다.
- **답글 위치:** 답글이 잘못 저장되던 것이 아니라, 목록을 시간순으로만 그려서 맨 끝으로 밀린 답글이 마지막 댓글에 달린 것처럼 보였다. 이제 원댓글 아래에 그 스레드의 답글을 시간순으로 모은다(`src/utils/commentThreads.ts`). 답글의 답글도 같은 원댓글 아래에 한 단계 들여쓰기로 놓인다.
- **답글 태그:** 답글 앞에 `@이름`이 붙는다. 서버가 `reply_to_name`을 저장하고, 예전 답글은 불러온 부모 댓글의 이름을 쓴다.
- **댓글 삭제:** 문서째 지우고 그 아래 답글도 모두 지우며, `comment_count`를 지운 만큼 줄인다. "삭제된 댓글" 표시는 없어졌다. 답글이 있으면 확인 창에서 함께 삭제된다고 알린다. 이미 남아 있는 `deleted: true` 문서는 앱에서 보이지 않지만 DB에는 남고, 그 아래 답글이 있었다면 `comment_count`가 실제보다 클 수 있다.
- **댓글 창 헤더:** "ㅇㅇ님의 러닝 이야기" 문구를 없앴다.
- **게시물 메뉴:** 알림 창 대신 아래에서 올라오는 목록(`ActionSheet`, 사진 고르기 시트와 같은 컴포넌트)이다. 내 글은 수정·삭제, 남의 글은 "이 게시물 보지 않음"과 "ㅇㅇ 차단"이다. 상세 화면의 연필·휴지통 버튼도 이 메뉴로 합쳤다.
- **이 게시물 보지 않음:** 바로 사라지고, 피드·탐색·저장함에 나오지 않는다. 그 사람의 프로필에서는 보인다. 숨긴 게시물을 되돌리는 화면은 아직 없다.
- **차단:** 확인 후 서로의 팔로우를 끊고, 기존 대화방을 막는다. 서로의 글이 피드·탐색·프로필에, 서로가 검색·랭킹·팔로우 목록에 나오지 않고, 서로 팔로우·응원·댓글·새 대화를 할 수 없다. 내가 차단한 사람의 댓글과 그 아래 답글은 보이지 않는다(나를 차단한 사람의 댓글은 다른 사람 글에서 보일 수 있다). 내가 차단한 사람의 프로필에는 차단 해제 버튼만 보이고, 나를 차단한 사람의 프로필은 열리지 않는다. 설정의 "차단한 사용자"에서 해제할 수 있으며 팔로우는 복구되지 않는다. 알림 등으로 게시물을 직접 열면 공개 글은 보일 수 있다.
- **카드 실시간 갱신:** 피드를 요청 방식으로 바꾸면서 응원·댓글 수와 수정·삭제가 카드에 반영되지 않던 문제를 함께 고쳤다. 카드마다 자기 글을 지켜본다.
- **서버 배포:** 사용자 승인 후 `dalryo-dev`에 `socialAction`과 `firestore.rules`를 배포했다(2026-11-03). 앞서 만든 새 대화 검색 순서도 함께 반영됐다. 앱의 로딩, 스레드, 태그, 메뉴 화면은 서버와 무관하게 동작한다.
- **검증:** Jest 602개, 에뮬레이터 서버 시나리오 28개, 규칙 시나리오 17개 통과. Android 에뮬레이터에서 앱을 완전히 껐다 켜 로딩이 걷히는 순간 캐릭터가 이미 그려져 있는 것을 프레임으로 확인했고, 게시물 메뉴 두 종류와 실제 댓글 데이터의 스레드·태그도 화면으로 확인했다. 이 계정의 캐릭터는 PNG로 그려져, Rive 경로의 준비 신호(재생 시작)는 Jest로만 확인했다. 그 신호가 오지 않는 기기에서는 최대 10초 뒤에 로딩이 걷힌다. 실제 서버의 삭제·보지 않음·차단은 배포만 했고 사용자가 직접 확인하기로 했다. iOS는 확인하지 못했다.
